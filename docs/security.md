# Security and privacy

## Data flow

The library processes local `Blob`/`File` objects and byte arrays in the browser. It does not upload those inputs to a service. If a string URL is supplied, the browser fetches that URL; the application and remote server remain responsible for network access, authorization, and CORS policy.

## Untrusted documents

Treat every document as untrusted input. The implementation applies the limits and validation below. They reduce exposure, but they are not complete protection, and the gaps are listed after them.

- The viewer defaults to a 128 MiB source limit, configurable with `maxFileSize`.
- ZIP reading defaults to 32 MiB per entry and 4,096 entries, and rejects unsafe paths, duplicate paths, encryption, multi-disk archives, ZIP64, and unsupported compression methods. When an archive is opened, every entry's local header must agree with the central directory (name, method, the encryption and data-descriptor flags, and the sizes and checksum, taken from the data descriptor where one is used), and no entry's record, including its data descriptor, may overlap another entry or the central directory; otherwise the archive is rejected.
- DOCX, PPTX, and XLSX packages may decompress at most 256 MiB of package data in total, like OpenDocument packages. This bounds decompressed data, not the page's total memory: parsed XML, the document model, and decoded images use memory in addition. Each part is decompressed and parsed at most once, however often the document refers to it; DOCX images are read only when the document uses them; repeated slide or sheet references are shown once; workbooks may have at most 1,024 sheets and 500,000 cells, and one XLSX cell at most 32,767 characters of text (Excel's limit); a workbook that exceeds either limit is refused rather than truncated; and an XML part larger than 1 MiB may expand at most 100 times its compressed size, so parsing work stays proportional to the size of the file.
- The XML parsers default to 250,000 elements, nesting depth 256, 16 MiB of source/text, 512 attributes per element, and 1,024 characters per name; DTDs and entity declarations are rejected, and there is no external entity resolution.
- External OOXML relationships are not followed to retrieve resources.
- The parsed document model of every format is limited while it is built, so a small file cannot produce a model that is expensive to keep or render: at most 6,000,000 objects and arrays, 67,108,864 UTF-16 code units of text, 256 MiB of image data, and a nesting depth of 64. Text is counted for every place it appears: a shared string counts again for each cell that uses it, and a cell's value and its formatted display text both count. A document that exceeds a limit is refused with a `resource-limit` error rather than truncated. The finished model is checked again against the same limits before it is rendered.
- OpenDocument spreadsheets have separate limits: `content.xml` or a whole `.fods` file 128 MiB, `styles.xml` 16 MiB, all parts together 256 MiB, 500,000 cells, 1,024 sheets, 32,767 characters per cell, and 10,000 elements per captured cell or style block. Exceeding one stops the preview with a `resource-limit` error rather than truncating content.
- OpenDocument text documents have their own limits: `content.xml` or a whole `.fodt` file 64 MiB, `styles.xml` 16 MiB, all parts together 256 MiB, 100,000 blocks (paragraphs, headings and tables), 100,000 table cells, 1,000,000 characters in one paragraph, 10,000 elements per captured paragraph, and 32 MiB for one image stored inline in a flat document. Table cells are charged as they are built, so a repeat count cannot multiply out before the limit applies. The XML elements of the content stream are bounded by the block budget (250,000 plus 24 per permitted block, so 2,650,000 at the default limit) and not by the size the part is allowed to have, on the same reasoning as for spreadsheets below. Exceeding one stops the preview with a `resource-limit` error rather than truncating content.
- An OpenDocument text document reads images only from its own package or, for a flat document, from the base64 data stored inline. A reference with a scheme, an absolute path or a parent-directory step points outside the document and is never followed or fetched; nor is a linked section, an embedded object or a template reference. Every image still goes through the same checks as any other: the media type comes from the bytes, SVG is sanitized, and the pixel limits apply.
- The XML elements of an OpenDocument content stream are bounded by the cell limit, not by the size the part is allowed to have: 250,000 plus eight per permitted cell (4,250,000 at the default limit), and three tokens per element. Every element in the stream counts, including those the parser then discards (styled empty cells outside the drawn grid, content-free covered cells, and skipped pivot-table or conditional-format subtrees), because reading them is the cost being bounded. A file that exceeds the budget is refused while it is being read. A compression-ratio limit is not used for OpenDocument parts, because ordinary spreadsheets compress beyond the 100:1 ratio applied to Office Open XML parts and an attack can be padded below any such threshold.
- Namespace resolution does not copy: entering an element costs only the declarations that element makes, and a prefix is resolved by walking the enclosing scopes, remembering the answer at each one. Entering an element used to copy every binding in scope, which nothing bounded, because the nesting and attribute limits together allow over 131,000 bindings at once: a few hundred elements below such a stack cost tens of seconds and more than a gigabyte while staying inside every element and token limit. This covers every document read with namespaces, which is OpenDocument files and SVG, standalone or embedded in XLSX and PPTX.
- Encrypted (password-protected) OpenDocument files are refused before any part is parsed. Macros are reported, not run; digital signatures are reported, not verified.
- OpenDocument external data (linked tables and DDE links) is never fetched, formulas are never evaluated, and only `http`, `https`, and `mailto` cell links are kept.
- Images are shown through `blob:` URLs, which have the origin of the page that creates them. All of them are created in one place:
  - Only PNG, JPEG, GIF, BMP, WebP, and SVG are accepted.
  - Raster images must start with a matching file signature, and the blob gets the type of the actual content, not the type suggested by a file name. Media whose content does not match is not shown.
  - SVG, both standalone `.svg` files and SVG media inside DOCX, PPTX, and XLSX packages, is reduced to an explicit allowlist first: only listed elements in the SVG namespace, only listed attributes without a namespace, each with a strict value rule (for example, paint values may refer only to an element inside the same image). The SVG is parsed by the library's own XML parser, not by the browser: a DOCTYPE or entity declaration, malformed XML, and characters XML does not allow make the image invalid. Comments, processing instructions, and CDATA are removed. The kept elements are written out again with escaped text and attribute values and a single SVG namespace declaration; that output is parsed again and must pass the same allowlist unchanged, otherwise the image is not shown. This removes scripts, event handlers, styles, and external references, and intentionally removes many SVG features.
- Font names from documents are accepted only when they consist of letters, digits, spaces, and a few punctuation marks; any other name is replaced by a generic family. Styles are set one CSS property at a time, so a value from a document cannot add other declarations.
- The viewer root (`.ufp-root`) uses `contain: layout paint style`, `isolation: isolate`, and `overflow: hidden`, so document content cannot be positioned or painted outside the viewer, even with `position: fixed`. Keep these declarations if you restyle the viewer. This also applies to your own elements: anything placed inside `.ufp-root` with `position: fixed` is positioned relative to the viewer and clipped to it, so put overlays such as dialogs and menus outside the viewer root.
- The XLSX formula evaluator implements a limited subset in project code. It does not use `eval`, execute macros, or fetch linked workbooks. Formula text results longer than 32,767 characters are `#VALUE!`, as in Excel, and number formats cannot produce more than 32,767 characters of text. Calculation has a work limit per workbook (formula cell reads and evaluations) and a nesting limit of 200 dependent formulas; past either limit, the remaining uncalculated formulas are shown as not calculated and the affected conditional formats and sparklines are left out. Conditional formats cover at most 1,000,000 cells per workbook, and their formulas count against the same work limit. Hyperlink ranges cover at most 1,000,000 cells, table filter buttons at most 100,000 columns, and slicers perform at most 2,000,000 row and filter checks per workbook (a slicer whose table needs more shows only the items read until then); the spreadsheet view limits the work spent on merged areas and column ranges.
- Raster images (standalone and embedded) are shown only when their header declares at most 40 megapixels, and one document may show at most 120 megapixels at a time. TIFF images in workbooks are converted only when their tile and strip sizes fit the image.

### Known gaps

- **Parsing runs on the page's main thread by default.** The limits above are meant to prevent a small file from causing disproportionate work (they were checked against the crafted cases in the test suite, not proven complete), but processing time still grows with the size of the file: a crafted file of a few megabytes, like a large legitimate one, can keep the page unresponsive for several seconds, and closing or replacing the viewer cannot interrupt a main-thread parse. **Worker mode** (the `worker` option, see the [API reference](./api-reference.md#worker-mode)) moves parsing of the document formats into a Web Worker: the page stays responsive, a parse that takes longer than the timeout (30 seconds by default) is stopped by terminating the worker, and closing or replacing the viewer stops it too. Receiving and rendering a large result still runs on the main thread (measured for the largest accepted workbooks: about 0.6 to 2.4 seconds, against 4 to 10 seconds of blocking in main-thread mode), and a worker shares the page's process: worker mode needs more memory at its peak than main-thread mode, not less.
- **Browser image decoding** runs in the browser process; this package cannot isolate the page from browser codec vulnerabilities. The pixel limits rely on the dimensions in the image header.
- **The limits are fixed.** They cannot yet be changed by the application.

Because of these gaps, previewing untrusted uploads can still make the browser tab unresponsive for a while. Do not rely on this library alone to protect an application that previews files from untrusted users; use the deployment guidance below.

## Deployment for untrusted files

- **Restrict input** to the formats and sizes your application needs (`maxFileSize`, and checks before calling the viewer).
- **Isolate the viewer** when documents come from other users. The strongest option is to render previews on a separate origin (for example a dedicated preview domain, embedded with an `<iframe>`), so that the preview page shares no cookies, storage, or same-origin access with your main application. Only a separate *site* (a different registrable domain, not a subdomain) lets browsers with site isolation run the preview in its own process; otherwise a preview that freezes can still freeze the embedding page.
- **Apply a Content Security Policy.** The viewer needs:
  - `img-src blob: data:` (images are shown from `blob:` URLs; spreadsheet pattern fills use `data:` SVG images);
  - no `'unsafe-inline'` in `style-src` in browsers with constructable stylesheets (tested in Edge, Chrome and Firefox; Safari is untested): the viewer adopts its stylesheet with `adoptedStyleSheets`, and the styles it sets on elements through the DOM are not restricted by CSP. In browsers without constructable stylesheets the viewer adds a `<style>` element instead, which such a policy blocks unless you pass its nonce as `styleNonce` (and allow that nonce in `style-src`) or allow `'unsafe-inline'`. The viewer cannot reliably detect that this fallback was blocked: the preview then appears unstyled;
  - `connect-src` for the origins you load documents from with string URLs (not needed for `File`, `Blob`, or byte-array sources);
  - in worker mode, `worker-src` (or `script-src`) allowing the origin that serves the package's `worker.js`, for example `worker-src 'self'`. No `blob:` or `data:` sources are needed in `script-src` or `worker-src`.

  A starting point for the page that hosts the viewer, to adapt to your application:

  ```
  Content-Security-Policy: default-src 'self'; script-src 'self'; worker-src 'self'; img-src 'self' blob: data:; style-src 'self'; connect-src 'self'; font-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'self'
  ```

  Not allowing remote origins in `img-src` and `font-src` also prevents a document from making the browser contact a remote server through CSS, should such a bug exist.

- **Trusted Types:** the viewer uses no markup sink (no `innerHTML`, no `DOMParser`): it builds its own elements with DOM methods and parses SVG with its own XML parser. It works under `require-trusted-types-for 'script'` without any Trusted Types policy (tested in Edge, Chrome and Firefox with `trusted-types 'none'`; Safari is untested). In worker mode, `new Worker(url)` in your `create` function is a Trusted Types sink: create the URL through a policy of your own that accepts only the worker script's URL, and allow that policy name in `trusted-types`. For example, with `trusted-types ufp-worker`:

  ```ts
  const policy = trustedTypes.createPolicy("ufp-worker", {
    createScriptURL: url => { if (url === workerUrl) return url; throw new TypeError("Unexpected worker URL"); },
  });
  const create = () => new Worker(policy.createScriptURL(workerUrl), { type: "module" });
  ```

## Application responsibilities

- Apply your own access controls before allowing remote URLs or local documents to be previewed.
- Do not treat parsed document contents as trusted application HTML. Use the library renderer output as designed and avoid reinserting document strings with `innerHTML`.
- Surface `PreviewError` appropriately without exposing sensitive URLs or document content in public logs.
- Call `destroy()` when a viewer is removed so object URLs and active requests are cleaned up.
- Keep the package updated and review security notices for both this project and supported browsers.

## Reporting a vulnerability

The project is maintained in [dukeofwest/universal-file-preview](https://github.com/dukeofwest/universal-file-preview). Use [GitHub's private security advisory form](https://github.com/dukeofwest/universal-file-preview/security/advisories/new) when private vulnerability reporting is enabled. The setting has not been independently verified in this documentation update. If GitHub does not offer the private form, do not disclose the issue in a public tracker; first contact the repository maintainer privately to arrange a monitored secure channel. Do not attach confidential documents. See [SECURITY.md](../SECURITY.md) for the policy.
